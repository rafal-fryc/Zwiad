# Zwiad Project Review & Improvement Roadmap

*Generated: 2026-04-10*

## Context

The Zwiad pipeline has grown significantly in one session: Phase 1 of the v2 dedup plan shipped (topic keys, `reports/index.json`, collision guard, scanner annotate post-process), the FPF Youth Privacy gap was closed, and IAPP was wired up as a third email source. This document audits what exists, flags real issues, and proposes a prioritized improvement roadmap.

Two parallel Explore audits ran over the codebase — findings below filter the genuine problems from false alarms (a few audit claims were wrong and are explicitly corrected).

---

## False alarms to dismiss

Before the real issues — two claims from the audits that were verified and rejected:

1. **"`dedup-findings.sh` pipe-to-while subshell bug"** — Incorrect. While bash subshells don't propagate *variables*, file appends with `>>` persist fine because the file handle is shared. The script was already run end-to-end against a synthetic test and correctly identified duplicates (both topic_key and URL matches). The pattern is ugly but not broken.

2. **"Scanner schema requires `topic_key` but agent says omit it"** — Incorrect. `pipeline/schemas/scanner.schema.json:12` only requires `id, title, source, source_url, summary, relevance, jurisdiction, development_type, category`. `topic_key`, `topic_type`, `topic_key_confidence` are all optional properties. The annotate post-process fills them before dedup. No drift.

## Real issues, ranked

### CRITICAL — breaks correctness or silently fails

**C1. Discord `/research` bypasses orchestrator Mode 2** (`discord_bot.py:600-740`)
The bot loops through findings and calls `claude -p --agent researcher` directly for each, then runs `run-reviewer.sh` via bash. This duplicates the orchestration logic that `.claude/agents/orchestrator.md` Mode 2 (lines 77-174) was designed to provide: the orchestrator handles sequential processing, escalation routing, error recovery, and topic_key passthrough. The bot's in-line version skips all of that.

**Fix**: Replace the bot's research loop with a single `claude -p --agent orchestrator --permission-mode acceptEdits` call with the Mode 2 prompt: `"Research phase for run {run_id}. Process approved findings."` Orchestrator then handles the per-finding loop internally. Delete the bot's `_run_reviewer` and the manual iteration logic.

**C2. Subprocess return codes unchecked everywhere** (`discord_bot.py:437, 479, 658-661, 689-691`)
Every `subprocess.run(...)` call in the bot ignores `returncode`. When `claude -p` exits non-zero or a bash script crashes, the bot proceeds as if the stage succeeded. The only safety net is "does the expected output file exist?" — which misses partial writes or stale files from a previous run.

**Fix**: Add a helper `_run_and_check(cmd) -> tuple[bool, str]` that returns `(ok, stderr_tail)`. On failure, post a Discord embed with the error. Apply to all four call sites.

**C3. IMAP fetch has no error handling** (`discord_bot.py:47-115`)
`fetch_new_emails()` opens an IMAP connection and does login/search/fetch/logout with no try/except around the network/IMAP operations. Any transient Gmail hiccup crashes the `/scan` command entirely — no user feedback, no partial results.

**Fix**: Wrap lines 56-113 in `try/except (imaplib.IMAP4.error, socket.error, OSError, Exception) as e:`. Return an empty list on failure and raise the error up to the caller so `/scan` can post a user-facing error message. Also set `imaplib.IMAP4_SSL("imap.gmail.com", timeout=30)` so hung connections don't freeze the bot.

**C4. `test-dedup.sh` is broken after the Phase 1 rewrite** (`tests/test-dedup.sh`)
The test copies a fixture scanner-output.json + a fixture existing report into `reports/privacy/`, then runs `dedup-findings.sh` expecting it to dedupe against the filesystem. The Phase 1 rewrite moved dedup to read `reports/index.json` exclusively — the fixture report is NOT in the index, so dedup won't catch it. The test will either fail or (worse) pass with wrong expectations.

**Fix**: Update the test to also call `tools/backfill_reports_index.py --promote` on the fixture before running dedup, or add a step that writes a minimal `reports/index.json` stub inside the test's temp space with the fixture's URL. Ideally migrate this test to pytest so it can mock the index path.

### HIGH — quality/observability gaps that will bite soon

**H1. No tests for the Python tools added in Phase 1**
`tools/topic_keys.py`, `tools/update_reports_index.py`, `tools/backfill_reports_index.py` have zero tests. The BILL_TYPE regex corpus (short + long forms), the year-default logic, the annotate idempotency contract, the atomic index writer — all untested. Regressions will be silent.

**Fix**: Add a `tests/test_topic_keys.py` pytest module. Parametrize:
- State bill handler: short form (`HB 351`), long form (`House Bill 351`), Legislative Document, Legislative Bill
- Enforcement handler: FTC/CAAG/CPPA examples with target + no target + end-of-string
- Rulemaking, guidance, fallback paths
- Idempotency: `annotate` twice on the same input → identical output
- Determinism: same finding with different ordering of fields → same key

Ship a minimal `pyproject.toml` with `[tool.pytest.ini_options]` so `pytest tests/` works without ceremony.

**H2. CLAUDE.md lies about dependencies**
CLAUDE.md says "No Python dependencies — agents use Claude Code's built-in tools" and "No external services — everything runs locally". Reality:
- `discord_bot.py` imports `discord`, `imaplib`, `email`, `dotenv` — all pip packages or stdlib
- `tools/bill_processor.py` uses `docling` (for PDF conversion) and Playwright
- `.env` holds IMAP credentials and the Discord token
- Scanner uses WebSearch which is an Anthropic-hosted API

**Fix**: Rewrite the "Installation & Setup" and "Runtime Environment" sections. List actual deps: `discord.py`, `python-dotenv`, `docling`, `playwright`, plus the claude CLI itself. Add a "Secrets" section documenting `.env` format and that IMAP uses a Gmail app password.

**H3. Topic key confidence lost in dedup fallback** (`pipeline/scripts/dedup-findings.sh:81-96`)
When the scanner doesn't emit `topic_key`, the dedup script computes one via `python3 tools/topic_keys.py --finding-json` and injects it back into the finding. But only the `topic_key` field is injected — not `topic_type` or `topic_key_confidence`. Downstream researcher + categorizer lose that signal and would have to recompute.

**Fix**: Swap the dedup fallback to read all three fields from the topic_keys.py output:
```bash
kv=$("$PYTHON_BIN" "$PROJECT_ROOT/tools/topic_keys.py" --finding-json "$finding" 2>/dev/null)
topic_key=$(echo "$kv" | jq -r '.topic_key // empty')
topic_type=$(echo "$kv" | jq -r '.topic_type // empty')
confidence=$(echo "$kv" | jq -r '.confidence // empty')
finding=$(echo "$finding" | jq -c --arg k "$topic_key" --arg t "$topic_type" --arg c "$confidence" '. + {topic_key: $k, topic_type: $t, topic_key_confidence: $c}')
```
Even better: the annotate step is already supposed to run between scan and dedup (orchestrator Mode 1 Step 2.5) — so the dedup fallback should rarely fire. Consider removing the dedup fallback entirely and making the annotate step mandatory/required.

**H4. Duplicate `normalize_url` implementations** (`pipeline/scripts/dedup-findings.sh:25-33` vs `tools/update_reports_index.py:35-45`)
Two independent implementations — bash sed pipeline and Python regex. Already drifting slightly. When URL normalization rules change (e.g., new tracking param), both must be updated in sync.

**Fix**: Delete the bash version. Have `dedup-findings.sh` call `python3 -c "from tools.update_reports_index import normalize_url; print(normalize_url('$url'))"` — or better, since dedup is already doing heavy per-finding Python work, move the whole URL normalization to a helper in `tools/url_norm.py` that both bash (via subprocess) and Python import cleanly.

**H5. Dead scripts taking up attention** (`pipeline/scripts/run-researcher.sh`, `approve-findings.sh`, `approve-escalation.sh`)
These are only referenced by `tests/test-*.sh` and other dead scripts. The production runtime (discord_bot.py + orchestrator.md) bypasses them entirely. Contributors trying to understand the pipeline hit these and get confused.

**Fix**: Either (a) delete them and update the tests, or (b) add a prominent comment at the top of each script explaining "LEGACY: This script is a CLI alternative to the Discord bot. The production flow uses the bot. Kept for standalone testing only."

**H6. `classify_emails` is hardcoded** (`discord_bot.py:118-148`)
Every new email source requires a code change + deploy. The function has hardcoded sender/subject string checks for FPF, IAPP, Lexology. Next source will need the same treatment.

**Fix**: Move the rules to `pipeline/config/email-sources.json`:
```json
{
  "sources": [
    {"bucket": "fpf", "sender_contains": ["fpf.org", "informz.net"], "subject_contains": ["fpf u.s.", "fpf youth privacy"]},
    {"bucket": "iapp", "sender_contains": ["iapp.org"]},
    {"bucket": "lexology", "sender_contains": ["lexology"]}
  ]
}
```
`classify_emails` loops over the config. Adding a new source = edit JSON, no Python change.

### MEDIUM — quality of life

**M1. No cost estimation or token accounting**
The research phase invokes Opus per finding (`claude -p --agent researcher --max-turns 20`). Each finding runs ~$0.05-$0.15. A 20-finding run costs a few bucks; a 200-finding run costs $30+. The user has zero visibility before or after.

**Fix**: After the scan phase, post a Discord message estimating: `"N approved findings × ~$0.08/finding ≈ $X to research. Proceed?"` Parse `claude -p --output-format json` responses post-research to extract `usage` fields and log total tokens + estimated cost to `pipeline/runs/{run_id}/cost.json`.

**M2. No `/status` Discord command**
User has no visibility into pending approvals, in-progress runs, or recently completed pipelines. Runs pile up in `pipeline/runs/` silently.

**Fix**: Add `/status` that walks `pipeline/runs/`, classifies each run by marker files (`scan-complete.marker`, `scanner-approved.json`, `pipeline-complete.marker`), and posts an embed with counts of each state.

**M3. No pre-flight health check**
Setup errors (missing `.env`, unauthenticated claude CLI, missing config files) only surface after a `/scan` attempt fails deep in subprocess land.

**Fix**: Add `/health` that verifies: `.env` present with required keys, `claude` CLI on PATH, `pipeline/config/*.json` present, `reports/index.json` valid JSON, `bills/tracker.json` valid JSON. Post a single embed with green/red per check.

**M4. `sys.path.insert` hack in backfill** (`tools/backfill_reports_index.py:37`)
The script does `sys.path.insert(0, str(PROJECT_ROOT / "tools"))` to import sibling modules. Fragile to CWD changes.

**Fix**: Add an empty `tools/__init__.py` and run scripts as modules: `python3 -m tools.backfill_reports_index`. Or use `importlib.util.spec_from_file_location` with an absolute path.

**M5. No central logging**
Print statements scattered across `discord_bot.py`, `tools/bill_processor.py`, `tools/backfill_reports_index.py`, and the bash scripts. Errors in an automated run go to different outputs — no unified audit trail.

**Fix**: Set up a single `logging` module config that writes to `pipeline/runs/{run_id}/audit.log` in addition to stdout. Import-and-go for Python; shell scripts use `echo "$(date) $*" | tee -a "$AUDIT"`.

## Integration question (not a bug, but worth deciding)

**I1. FPF bills and `reports/index.json` are separate universes**
The FPF path terminates at `bills/tracker.json` — FPF bills are never researched, categorized, or cross-indexed with Lexology/IAPP reports. If Lexology publishes a story about Alabama HB 351 AND the FPF scanner picks up the same bill, there's no relationship between them. The reports/index.json has no bill keys; the tracker has no report paths.

**Options**:
- **Keep separate** (current state). FPF is a data-tracking pipeline; reports/ is a narrative-report pipeline. They serve different purposes.
- **Cross-index**: When bill_processor.py adds a bill to tracker, also add a thin "bill_ref" entry to `reports/index.json` with a `topic_key` matching the bill key. When the scanner sees a finding with an already-tracked bill, it can link it.
- **Full unification**: Generate a one-page report per FPF bill (description + current status + bill text URL) and categorize it into `reports/privacy/state-legislation/`. Researcher writes these for high-signal bills only.

**Recommendation**: Cross-index only (option 2). Full unification is too expensive (1 report per 500+ bills). Cross-indexing is cheap — just add a synthetic entry to `reports/index.json` per bill, no narrative text.

## What is NOT recommended

To keep this actionable, a few things were deliberately excluded:
- Rewriting dedup-findings.sh as Python (the shell version works; Python rewrite is invasive for marginal gain — revisit if H3/H4 don't settle the pain)
- Typing every Python function (too much churn; add types opportunistically as bugs surface)
- Introducing a database (filesystem JSON is fine at current scale; revisit at 5K bills or 500 reports)
- Restructuring `pipeline/scripts/` into a Python package (too invasive for a solo dev operating via Discord)
- Adding a web UI or dashboard (Discord is the UX; a `/status` command is enough)

These are all reasonable future investments but not where the pain is today.
